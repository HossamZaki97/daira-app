# دايرة — إعادة تصميم تجربة نسخة Odoo

**الحالة الحالية: طُبّقت خطة التصميم على Flutter لنسخة Odoo.**

المعاينة الفعلية من Flutter: [flutter-preview.png](flutter-preview.png)، ببيانات اختبارات توضيحية.
النموذج أدناه وشرح تسليمه الأول سجل تصميم مستقل؛ مرجع التنفيذ الأحدث هو خطة التنفيذ.

خطة التنفيذ المبنية على مراجعة الكود والبيانات:
[خطة التنفيذ ومعايير القبول](IMPLEMENTATION_PLAN.md).
بدأ التنفيذ بعد تأكيدك؛ الخطة أحدث من أمثلة المعاينة التوضيحية.

ملف Figma المستهدف: [Daira — Odoo App Revamp](https://www.figma.com/design/fygsh7qTdLuTvd0nqwSpV3/Daira---Odoo-App-Revamp).
وجود الرابط لا يعني أن الملف عُدّل. عندما أُعد هذا التسليم لم تظهر أدوات Figma
المتصلة في جلسة الوكيل؛ البديل المتاح هو استيراد لوحة SVG أدناه.

## افتح التصميم

- `index.html`: نموذج محلي تفاعلي؛ افتحه في المتصفح. يستخدم ملفات الخط والشعار
  داخل المشروع، ولا يحتاج اتصالًا بـOdoo. يمكن أيضًا مراجعته على
  `http://127.0.0.1:8096/design/revamp/index.html` عند تشغيل خادم المعاينة المحلي
  بالأمر `python design/revamp/review_server.py`. الخادم لا يعرض config أو ملفات Git.
- `screen-atlas.svg`: لوحة من **36 مجموعة شاشات** قابلة للاستيراد إلى Figma.
- `design-preview.png`: معاينة واحدة لأربع شاشات محورية؛ وهي تصيير فعلي
  لـ`design-preview.svg`، وليست صورة مولّدة بالذكاء الاصطناعي.
- `design-tokens.json`: الألوان الدلالية والمقاسات والأوزان والمسافات المقترحة.

لا توجد بيانات حقيقية في هذه الملفات. الأسماء والمبالغ والتواريخ والرموز أمثلة.
التفاعلات محاكاة محلية، ولا تنشئ حسابًا ولا تسجل إقرارًا أو اعتمادًا على Odoo.
لا يُحفظ رمز دعوة أو كلمة مرور أو جلسة في التخزين المحلي للنموذج.

## الاتجاه: «كل دور واضح»

شخصية هادئة، اجتماعية وموثوقة. لا تشبه محفظة استثمار أو تطبيق تداول.
تُعرض الخطوة التي يحتاجها المستخدم الآن بدل مساحة ترحيب كبيرة متكررة.
المبالغ التي لها معنى تبقى بارزة؛ الأرقام الزخرفية والإجماليات المختلطة تُحذف.

يستخدم التصميم الآن الشعار المعتمد في `design/brand/people-circle/`، برمز أزرق
على الأبيض وثلاثة أفراد متساوين. نُفّذ الشعار داخل Flutter وموارد Launcher بعد اعتماد التنفيذ، مع الحفاظ على هندسته.

| العنصر | المقترح | الوظيفة |
|---|---|---|
| الأزرق الأساسي | `#356DF3` | الإجراء الأساسي وهوية دايرة |
| كحلي الحبر | `#142C50` | التركيز على مبلغ أو خطوة حالية |
| سماوي دايرة | `#087F8C` | تمييز اجتماعي محدود، لا حالة مالية مستقلة |
| الخلفية | `#F5F7FB` | فصل هادئ بين المحتويات |
| النص | `#182943` | القراءة والعناوين |
| الخط | Cairo، أوزان 400/600/700 | يظل متسقًا مع الأصول الموجودة |

الأخضر للاعتماد/الإتمام، الكهرماني للانتظار، الأحمر للخطأ أو التأخر. تترافق
الحالة مع نص وأيقونة، ولا يُطلب من المستخدم فهم اللون وحده. لا تدرجات ثقيلة،
لا ظلال داخلية، ولا عملات ذهبية أو مؤشرات مالية زخرفية.

## بنية التنقل

تبقى أربع وجهات رئيسية واضحة: **الرئيسية، جمعياتي، الإجراءات، الإعدادات**.

1. **الرئيسية:** خطوة واحدة ذات أولوية، آخر تحديث، ثم بطاقات الجمعيات. حد أقصى
   ثلاث التزامات عند تطبيق التصميم؛ إذا زادت توجد وصلة «كل الإجراءات».
   لا تُكرر CTA المالية في بطاقة الترحيب وبطاقة اختصار أخرى.
2. **جمعياتي:** فلاتر بعدادات بصيغة «النشطة (2)»، مبلغ القسط لكل سهم وعملته،
   الدور الحالي وحالته. المسودات لها مسار «متابعة الإعداد».
3. **الإجراءات:** مطلوب منك، بانتظار الآخرين، أُنجز مؤخرًا. لا عنوان لقسم فارغ.
   الشارة تحسب فقط الإجراء الذي يستطيع الحساب تنفيذه، لا عدد الأعضاء المتأخرين.
4. **داخل الجمعية:** الدور الحالي، الأعضاء، النشاط. الجدول والأدوار القادمة
   داخل سياق الجمعية، وليست طبقة أخرى في شريط التنقل الرئيسي.
5. **الإعدادات:** الحساب الحالي والبريد المؤكد، اللغة، المظهر والاستعادة والخروج.
   لا صورة ملف شخصي أو بيانات إضافية لا يدعمها المنتج الحالي.

## الرحلات المصممة

| الرحلة | الشاشات والحالات | قرار الاستخدام |
|---|---|---|
| الحساب | دخول، إنشاء، تأكيد، إعادة إرسال، استعادة، كلمة جديدة، رابط منتهي | رسالة التسجيل محايدة؛ دائمًا يوجد مسار دخول أو استعادة أو بريد آخر |
| البداية | حالة بلا جمعيات، إنشاء أو انضمام | CTA واضحة، دون جمعيات أو مبالغ تجريبية تبدو حقيقية |
| إنشاء جمعية | الأساسيات ← الأعضاء والأسهم ← الدورية والجدول ← المراجعة | تقليل عبء النموذج؛ حفظ مسودة؛ تأكيد منفصل قبل التفعيل |
| التحصيل | قسط مطلوب ← تأكيد الإبلاغ ← انتظار الاعتماد | لا طلب رقم تحويل أو طريقة دفع أو صورة |
| المراجعة | بيانات العضو والمبلغ ووقت الإبلاغ ← اعتماد أو رفض | الاعتماد يحتاج تأكيدًا؛ الرفض يحتاج سببًا حتى 500 حرف |
| التسليم | التحصيل مكتمل ← إقرار المنظم ← تأكيد المستفيد | ثلاث حالات منفصلة؛ لا تحويل مالي داخل التطبيق |
| الأعضاء | أنت + المنظم، الأسهم والأدوار، العضوية المرتبطة | الشارة مرتبطة بـuser_id، دون استنتاج من الاسم |
| الدعوة | إنشاء/مشاركة/نسخ، دعوة فعالة، فقدان السر، إلغاء أو استبدال | لا إلغاء تلقائي؛ استبدال صريح مع تأكيد قبل إبطال الرمز السابق |
| الانضمام | إدخال رمز ← معاينة اسم الجمعية والعضوية ← قبول | لا تفاصيل مالية حساسة قبل القبول؛ ظهور الجمعية بعد رد الخادم |
| الفشل | تحميل، انقطاع، تعارض، صلاحية غير كافية، انتهاء جلسة | لا نجاح وهمي ولا عرض استثناءات SQL أو أخطاء تقنية للمستخدم |
| الإتمام | آخر تأكيد استلام ← اكتمال الجمعية ← سجل متاح | لا وصف التحصيل وحده بأنه تسليم أو تحويل |

شاشة تعيين كلمة المرور تمثل صفحة Odoo الآمنة التي تُفتح من رسالة الاستعادة؛
التصميم لا يفترض وجود تغيير كلمة مرور جديد داخل التطبيق.

## الحالات والصلاحيات التي يجب الحفاظ عليها عند التنفيذ

| حالة الدور/القسط | من يتصرف؟ | CTA |
|---|---|---|
| Pending، بما فيه المتأخر | صاحب الالتزام | أبلغت بالدفع |
| Reported | المنظم فقط، بما في ذلك قسطه بعد خطوة الإبلاغ | مراجعة الإقرار |
| Reported لعضو عادي | ينتظر المنظم | لا CTA اعتماد أو رفض |
| Approved | لا إجراء على القسط نفسه | إظهار التالي عند وجوده |
| Ready for payout | المنظم فقط | تسجيل تسليم الدور |
| Payout reported | المستفيد المحدد فقط | تأكيد الاستلام |
| Receipt confirmed | يُتاح الدور التالي حسب منطق الخادم | متابعة الدور التالي |
| آخر Receipt confirmed | لا دور تالٍ | الجمعية مكتملة |

الإبلاغ والاعتماد خطوتان منفصلتان حتى عند المنظم نفسه. الرفض يعيد الالتزام
للحالة التي تسمح بالإبلاغ مجددًا، مع إظهار السبب. تعطيل الزر أثناء الإرسال
والاحتفاظ بمعرّف العملية عند إعادة المحاولة يظلان مطلوبين. لا نجاح قبل رد Odoo.

كل مبلغ يتبع الجمعية وعملتها ووحداتها الدقيقة. لا رصيد افتراضي ولا مجموع بين
الجنيه والريال. عبارات «المعتمد تحصيله» و«المتبقي للاعتماد» تميّز السجل عن حركة
النقود. الأدوار التاريخية المستوردة تُعرض بصفتها تاريخية، دون دليل تسليم مُختلق.

## المكوّنات والتكيف

- شبكة مسافات من مضاعفات 4؛ الأساس 8، هامش الشاشة 20–24.
- عناوين 24–28، أقسام 16–18، نص أساس 14–16، مساعدة 12، مبالغ 28–38.
- زر أساسي واحد لكل قرار، لا يقل عن 48×48؛ النص يلتف بدل التصغير التلقائي.
- المكونات: App header، Action hero، Circle card، Member row، Status chip،
  Amount، Timeline، Sticky action، Bottom sheet، Inline error، Empty state.
- دعم RTL/LTR فعلي: تُعكس اتجاهات التنقل، وتُعزل الرموز والمبالغ والبريد.
- الشارة «أنت» مع «المنظم» تبقيان متجاورتين وتلتفان عند الحاجة.
- Footer ثابت خارج المحتوى القابل للتمرير؛ آخر عنصر يظل فوقه. الحقول تراعي
  لوحة المفاتيح، والشيت قابل للتمرير، والعنوان المالي لا يُقص.
- عند 320×568 وتكبير 1.5 تُكدّس الملخصات والأزرار رأسيًا إن لم تتسع، وتصبح
  التبويبات قابلة للتمرير. يجب فحص ذلك على Flutter بعد التنفيذ.
- النص الداكن/الثانوي والحالات والأزرار الرئيسية اجتازت مراجعة تباين 4.5:1
  للأزواج المحددة في الاختبارات، وهذا لا يُعد تدقيق WCAG شاملًا.
- حركات قصيرة 150–180ms، وتُلغى عند تفضيل تقليل الحركة.

## الاستيراد إلى ملف Figma

1. افتح ملفك في وضع **Design**.
2. اسحب `screen-atlas.svg` إلى مساحة فارغة، أو استخدم Place image وحدد SVG.
3. سيظهر كمتجهات ونصوص ضمن مجموعات مرقمة. اختر المجموعة وUngroup عند الحاجة.
4. تأكد من توفر خط Cairo، ثم حافظ على صفحة مستقلة باسم `01 — Proposed UX`.

**حدود SVG:** ليس ملف `.fig`، ولا يحتوي تلقائيًا على Figma Variables أو
Auto Layout أو Component variants أو Prototype connections. الأشكال والنصوص
قابلة للتحرير؛ مرجع التفاعلات هو `index.html`. إن توفر الاتصال المباشر لاحقًا،
يُستكمل التنظيم كمكوّنات وAuto Layout داخل الملف نفسه دون تكرار الاتجاه.

## المراجعة والتحقق

- فُحصت معاينة SVG المصيّرة بصريًا، وأُصلح اتجاه محاذاة العربية.
- اختبارات النموذج تحققت من السيناريوهات الأساسية، انتظار التأكيد، الصلاحيات
  الظاهرة، الانضمام ومعاينة العضوية، فصل التحصيل والتسليم والاستلام، والتحقق
  من السبب والتباين. تم توليد 28 شاشة/حالة في أربع توليفات لغة/مظهر.
- هذه اختبارات DOM ومنطق محاكاة؛ **لا تثبت عدم overflow في متصفح حقيقي أو
  على الهاتف**. لم تُعد اختبارات Flutter أو Odoo لأن كودهما لم يتغير.
- الروابط إلى الحسابات في النموذج أمثلة، ومشاركة النظام معروضة كتفاعل إرشادي؛
  لا يحدث إرسال فعلي. إنشاء الجمعية يسمح بإضافة الأعضاء ومراجعة الأقساط والأسهم والجدول، لكنه يظل
  محاكاة منفصلة عن Odoo وليس نسخة من تطبيق الإنتاج.

لإعادة التوليد: `python design/revamp/build_atlas.py`.
للاختبارات الاختيارية: ثبّت jsdom في بيئة أدوات خارج المشروع، ثم عرّف
`JSDOM_PATH` وشغّل `node design/revamp/check_prototype.cjs`.
لا يضيف التسليم dependency إلى التطبيق ولا يقرأ config محليًا أو بيانات مستخدمين.

## التطبيق بعد المراجعة

اعتماد الاتجاه البصري أولًا، ثم تنفيذ tokens والمكونات المشتركة، ثم التنقل
والرئيسية والجمعيات، ثم Auth والدعوات، ثم شاشات المال مع إبقاء Domain وOdoo
مصدر الحقيقة. عندها تُفحص الشاشات المتغيرة على 320 و390، العربية والإنجليزية،
Light/Dark، وتكبير 1.5، مع اختبارات الصلاحيات والحفظ التي يمسها التغيير فقط.

التسليم الأول كان تصميمًا فقط. تفاصيل التنفيذ اللاحق وتعديلات القراءة وAuth ونتائج الفحوص في خطة التنفيذ.


## تحديث المراجعة بعد اعتماد الشعار

- استُخدم أصل الشعار المعتمد في النموذج ولوحة الشاشات، مع ملف مقاسات مستقل.
- فُحص الشعار عند 24 و32 و48 و96 و192 و512 بكسل. لعرض 24 فقط توجد محاذاة
  شبكية بإزاحة ربع بكسل، مع بقاء الهندسة نفسها؛ المصدر الأساسي متمركز بدقة.
- أصبحت معاينة الإنشاء تستجيب للأعضاء والأسهم والدورية والتاريخ، وتوضح الفرق
  بين عدد الأعضاء وعدد أدوار الاستلام. الحساب في المعاينة بوحدات العملة الدقيقة.
- يعمل زر إضافة عضو، ويمكن حذف الصف الإضافي قبل التفعيل. الحقول الناقصة تمنع
  المتابعة وتُحدد برسالة قريبة مع توجيه التركيز إلى الحقل.
- تعرض المراجعة قيمة كل دور وبيانات الأعضاء والمواعيد، ويمكن الرجوع للقسم
  المناسب دون فقد الإدخال. تُعرض ثلاثة مواعيد أولًا مع إتاحة الجدول الكامل.
- تُقبل الأرقام العربية والإنجليزية، وتُرفض الكسور الزائدة على دقة العملة.
- أزيلت رسائل داخل التطبيق تشرح حساب الشارة للمستخدم؛ الإجراء نفسه هو الأهم.
- خُصص تنسيق مكدّس للمساحات الضيقة وتكبير النص، مع استمرار Footer خارج
  منطقة التمرير. اختبار DOM لا يثبت شكلها على الهاتف؛ فحص الجهاز يتبع التنفيذ.
- اعتُمد التنفيذ وأُنجز؛ راجع حالة كل جزء وحدود التحقق في خطة التنفيذ.

نجحت 26 مراجعة آلية خاصة بالنموذج، مع اختبار تحميل ملفات الصفحة الفعلي عبر
الخادم المحلي وتنفيذ مسار الإنشاء والمراجعة والرجوع للتعديل. لا تمثل هذه
المراجعات اختبار Flutter أو فحص overflow بصريًا على جهاز حقيقي.
